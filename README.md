# zensical-dyalog

The Dyalog user documentation as a single flattened [Zensical](https://zensical.org) project,
ported from the MkDocs monorepo at [dyalog/documentation](https://github.com/dyalog/documentation).

The monorepo split existed only to keep author build times tolerable across ~3,050 markdown
files. Zensical's differential builds remove that constraint, so the 14 sub-projects are
flattened into one project here. Every public URL from the monorepo is preserved, so existing
links keep resolving.

This repository is generated out-of-place from the monorepo source by a conversion script
(retained under tooling until cutover) and becomes the authoring home once Zensical reaches
parity. The phased migration is described in
[design/plans/zensical-port-plan.md](design/plans/zensical-port-plan.md).

## Status

The tooling port (checks, maintenance scripts, CI and release workflows) is in progress. The
cutover replays the move to Zensical on a clone of `dyalog/documentation`
(`tools/cutover/cutover.py`); `tools/cutover/README.root.md` becomes the repository's README
there.

`zensical/` is a like-for-like conversion of `dyalog/documentation` at 0afe7b461b
(19 November 2026), regenerated by `tools/cutover/convert.py` with no hand edits on top. The
earlier authored-in-place experiments (Diátaxis tags, Tutorials and How-to hubs, the ⎕CSV
rewrite, the "Was this page helpful?" widget) were discarded on 17 November 2026.

The build is stock Zensical plus one stylesheet, the house style, kept in its own repository
[xpqz/documentation-theme-zensical](https://github.com/xpqz/documentation-theme-zensical) and
mounted as a submodule at `zensical/docs/documentation-theme-zensical/`. The house classes the
MkDocs stylesheet styled were rewritten into plain Markdown at conversion time (see
`tools/cutover/transforms.py`), and [design/asset-switch-issues.md](design/asset-switch-issues.md)
records the design. Design notes, plans and reviews live under [design/](design/).

## Contributing and local builds

Setup, previewing, the checks and the authoring conventions are in [CONTRIBUTE.md](CONTRIBUTE.md).
Note that [Dyalog/documentation-guidelines](https://github.com/Dyalog/documentation-guidelines)
still describes the old MkDocs markup.

## Regenerating from the monorepo

With a checkout of `dyalog/documentation` as a sibling directory named `documentation`:

```
uv sync --all-groups
uv run python tools/cutover/convert.py --regenerate   # rewrites zensical/ (keeps the house style submodule)
uv run python tools/check.py                   # builds it and runs every check
```

`convert.py` refuses to run when a page in `tools/cutover/content/` (a hand-reworked replacement) no
longer matches the source page it was written against; re-merge and update the `.source-sha256`
sidecar. Each guide is mounted at the path mkdocs-monorepo-plugin gave it on the live site, its
slugified `site_name`: for the two .NET guides that is `net-interface-guide/` and
`net-framework-interface-guide/`, not their directory names.

The monorepo's `macros` plugin is not carried over: macros are not available. The corpus used it
only for version numbers, so the `dyalog_vars` Markdown extension (`tools/dyalog_vars.py`)
substitutes `{{ name }}` with the scalar of that name in `[project.extra]` instead, for example
`{{ version_majmin }}`.

## Reviewing code examples

`tools/cutover/code-blocks.py` proposes splitting the session examples in the language reference
guide's `apl` blocks into input (`apl`) and output (`text`), runs them in Docker (one locked-down
container per run, removed at the end, a fresh interpreter per page, no network; the image is built from `tools/cutover/docker/Dockerfile` when
missing), and writes a review log (it edits `zensical/` only with `--apply`). Examples never run on the host;
results are those of Linux Dyalog 21.0 in that image. Without Docker it only proposes splits.

```
uv run python tools/cutover/code-blocks.py --log code-blocks.yml
```

With `--define-shown`, a block that shows a variable the page never defines (`      M` followed by
its printed value) is proposed with an array-notation definition in its place, such as
`M←[10 20 30 40` / `   50 60 70 80]`, but only when a further run proves it: the name then
displays the printed value and the block matches.

Set each entry's `decision` to `apply` or `skip`; reruns keep decisions whose proposal is
unchanged. Then apply the reviewed entries to `zensical/docs` (input in an `apl` fence, output in a
`text` fence), or, with `--match-only`, every entry whose verdict is `match` (never one marked
`skip`); `--dry-run` reports without writing, and a block changed since the log is left alone:

```
uv run python tools/cutover/code-blocks.py --apply --log code-blocks.yml [--match-only] [--dry-run]
```

`zensical/docs` is regenerated from the source by `convert.py --regenerate`, which discards applied
changes; apply as the last step of the cutover. Applied pages read back: an `apl` fence followed by a `text` fence is
one block (split `already`), so the tool can check them again. The options, the log's fields and every verdict, reason and split value are described in
the module docstring.
